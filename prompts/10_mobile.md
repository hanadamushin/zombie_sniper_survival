# 10 スマホ対応（任意・低優先）

あなたはスマートフォン（タッチ操作）対応の担当です。PC 版が完成している前提で、
**PC 版の挙動を一切変えずに**、タッチでも一通り遊べるようにします。完璧な操作性よりも「破綻なく遊べる」を目標に、小さくまとめてください。

## 作業の前提（毎回最初に確認。発注者の許可済み）

- このセッションは GitHub リポジトリ `hanadamushin/zombie_sniper_survival` へ**プッシュできる状態**で作業する。作業ディレクトリにリポジトリが無い、または読み取り専用でしか複製できない場合は、**最初に**リポジトリを書き込み権限つき（push）でセッションに追加し、複製してから作業を始めること。**発注者はこの追加とプッシュを事前に許可している**（このプロンプト自体が発注者からの指示）
- 作業の最後に、指定のブランチへプッシュしたうえで、`git ls-remote` でリモートのブランチがローカルのコミットと一致することを確かめてから終える。プッシュできないまま終えない

## ゴール（M8）
スマホの横画面で、狙撃・回収・指揮・地図の全操作ができる。

## 実装範囲
1. **入力層**: タッチ入力から同じ `InputFrame` とコマンドを生成する（sim 側は変更しない）。端末判定はポインタ種別で行い、PC とは自動で切り替える
2. **戦術層の操作**
   - 左: 仮想スティック（移動）／右: ドラッグで視点
   - ボタン: スコープ（トグル）、射撃、息止め（押している間）、リロード、姿勢切替、ナイフ、回収
   - スコープ中の視点感度は倍率に応じて下げる。微調整用に **ジャイロ照準**（任意でオン、許可ダイアログ対応）
   - 倍率はスライダー、ゼロインは ± ボタン
   - 照準補助は入れない（狙撃の手応えを保つ）。代わりに息止めの効果時間をタッチ時のみ +30%
3. **指揮層・戦略層**: ピンチでズーム、ドラッグでパン、タップで選択、長押しで詳細。壁・堀の線引きはドラッグ。パネルは下からのシート表示
4. **レイアウト**: 横画面固定の案内（縦のときは回転を促す）、セーフエリア対応、ボタンは 44px 以上
5. **性能**: 画質プリセット「低」（視程 500m、草なし、同時ゾンビ 60、解像度スケール 0.75）を自動適用。設定で変更可
6. **PWA（余力があれば）**: manifest とアイコン（コード生成）、全画面表示

## やらないこと
- ゲーム内容・バランスの変更、PC 操作の変更、ネイティブアプリ化

## 受け入れ基準
- Playwright のモバイルエミュレーション（横向き）で、新規ゲーム → 1体狙撃 → 耳回収 → 指揮層で柵を1本配置、が通る
- PC での `npm run check` と e2e が引き続き通る（PC の挙動が変わっていない）
- モバイル相当の設定で 30fps 以上（計測値を PROGRESS.md に）

### 06 の結果を受けて

- 建築の操作はマウス前提（`ui/command/build.tsx` の `BuildGround`: 左ドラッグで連続配置／視点移動、右ドラッグで回転、ホイールで拡大）。Pointer Events で書いてあるので、1 本指 = 配置・移動、2 本指 = 回転・拡大の対応を足せる。幅 360px でも崩れないことだけ確認済み

### 07c の結果を受けて

- ゾンビは区域あたり最大 600 体、周囲 3×3 の区域を描画している。画質プリセット「低」では、同時出現の倍率（`BALANCE.world.activeMul`）ではなく **描画側** を絞る（遠くのゾンビの簡略化しきい値 `RENDER.zombies.lodPixels` を上げる、隣の区域を描く距離 `RENDER.terrainLod` を縮める、視程を 500m に）。sim の数を端末で変えると、同じセーブで遊びが変わるため
- Web Worker（`render/tactical/mapWorker.ts`）で隣の区域を作っている。iOS Safari での Worker と転送の動作を確認すること

### 08 の結果を受けて

- HUD の部品は画面の縁に寄せてあり、ポインタを受けるのは `#ui button` だけ。幅 480px 以下で上部バーが 2 段（`--hud-h: 64px`）。タッチのボタンはこのデザイントークン（`ui/styles.css` 冒頭の CSS 変数）で作る
- 毎フレーム動く表示は `ui/live.ts` の `useLive`（Preact を通さない）。仮想スティックやゲージもこの仕組みに載せる
- 音は最初にキー／ボタンを**離した**ときに AudioContext を作る。タッチでは `touchend` / `pointerup` で同じ処理を呼ぶ（iOS は利用者の操作の中でしか音を始められない）
- 設定画面（`zss.settings.v1`）に、タッチ用の感度とジャイロのオン／オフを足す
- 07e で賃金が小数（0.1 刻み、例「賃金 0.9/日」）になった。狭い画面の生存者の行で桁が増えても崩れないか確認する

## 07d-1 からの注意
- 中に入れる建物の描画は 1 区域で最大 7 ドローコール（`render/tactical/enterables.ts`）。内部を出す距離 `RENDER.enterables.near`（40m）と外観の距離 `mid`（300m）が三角形を決める。端末が重いときはこの 2 つを下げる
- 屋内は天井が低く狭い。タッチの視点操作で壁に寄りすぎないよう、カメラの near（0.1m）と人の半径（0.35m）の関係はそのまま保つこと

## 07d-2a からの注意
- 狭小 3 階建て・アパートの階段は幅 0.9m の折り返し、木造アパートの外廊下は内幅 1.14m。タッチの移動で壁に引っかかりやすい場所なので、仮想スティックの微調整（低速）を確かめる

## 07d-2b からの注意
- ビジネスホテル（10 階）の折り返し階段は 9 回上り下りする。タッチの移動で階段の踊り場に引っかからないか確かめる。回転寿司の通路（幅 1.8〜1.9m）とコンビニの通路（1.2〜1.4m）はブースや棚に挟まれて狭い

## 07d-2c からの注意
- 超高層（32 階）は折り返し階段を 32 回上る。タッチの移動で踊り場の角に引っかからないか、上り続ける操作が辛くないか（自動で上る補助を検討）を確かめる。百貨店の止まったエスカレーター（幅 1.0m の直階段）は両脇に手すりがある
- 内部の三角形は入れる階で 1 階あたり最大 2,800 前後（百貨店・庁舎風・商業ビル）。`RENDER.enterables.near` を下げると端末の負担が減る

## 07d-2d からの注意
- 公共施設は大きい（学校・大学・大病院は 50〜100m 四方の敷地、8 階まで）。屋内の移動・階段・屋上の操作をタッチで試すなら、大病院の 8 階や消防署の望楼（細い階段塔）が厳しめの例になる

## 07d-2e からの注意
- 駅・空港は 1 つの設計図が最大 850 × 280m で、外観の三角形が最大 7,300（政令市の駅。上限を 8,000 に上書き）。内蔵 GPU の性能 3 指標は PROGRESS.md の 07d-2e の表。モバイルでは外観の段階（300m）を縮めるのが効く

## 07d-2f からの注意
- 自衛隊の大の駐屯地は 750 × 500m（区域の大半）で外観 1 万三角形を超える（上限を 12,000 に上書き）。中に入ると敷地全体の内部が描かれる（約 2 万三角形）。金庫・弾薬庫の操作は E を 1 回押すだけ（長押しは使っていない）

## R0 からの注意（R0 が追記）
- 実在の区域ファイル（`public/data/areas/<地方>/*.bin`、1 つ平均 約 16KB の gzip）は区域に入るときと隣へ歩くときに fetch する（`src/realData.ts`）。全国で数十 MB になるので、オフライン対応（Service Worker のキャッシュ）を入れるなら地方単位で
- 出典の画面（`src/ui/components/Credits.tsx`）は縦長の一覧。幅 360px で崩れないことは確認済みだが、タッチのスクロールは未確認

## 07d-3 からの注意（07d-3 が追記）
- 町の区域は中に入れる建物が 1 区域に最大 約 1,300 棟（札幌の北）。外観・内部の段の三角形は描く全区域で合わせて `RENDER.enterables.triBudget`（14 万）まで、近い順（超えると遠景の箱のまま）。モバイルの GPU で重ければこの予算と `mid`（300m）を下げる
- 屋内のゾンビの配置は 1 ステップに 3 棟ずつ設計図を作る（区域に入った直後の数十ステップ）。端末で区域に入った直後にカクつくなら `BALANCE.zombie.indoor.buildingsPerStep` を 1 に

## L9 からの注意（橋の名所）
- 橋の名所は 1 本で 1,800〜7,000 三角形、霧の先（900m）まで外観で描く（明石海峡大橋は 2 区域にまたがり、隣の区域の分も描かれる）。モバイルで重ければ、橋の名所だけ遠くでハンガー・トラスの斜材を省く段を `bridge.ts` に足す（形の数は主塔・ケーブル・桁で分かる）
- 桁の上を歩く当たり判定は、陸の区間で見えない箱（2m 格子を行ごとにまとめたもの、1 本で数百〜1,900 個）。設計図の当たり判定の作成は橋に近づいたとき 1 回（`detailOf` の LRU）

## L10 からの注意（普通の橋・長い橋）
- 普通の橋は 1 本 600〜2,700 三角形、名所と同じく霧の先（900m）まで外観で描く。最も多いセルで橋だけ 1.5〜2 万三角形。モバイルで重ければ普通の橋だけ遠い段で欄干・車線・線路を省く（`bridge.ts` の `ramp` の呼び出し）か、`RENDER.enterables.landmarkFar` を普通の橋だけ短くする
- 水の上の桁を歩く当たり判定は見えない箱（普通の橋 1 本で 200〜2,300 個、名所の橋は全長）。設計図の当たり判定は近づいたとき 1 回（`detailOf` の LRU）。区域の生成時間は橋の多い都心のセルで 600ms 前後
- 表 `src/data/bridges/ordinary.ts` は 160KB（gzip 約 45KB）で本体の JS に入る。読み込みが重ければ地方ごとに分けて区域ファイルと一緒に読む形に変える（両側の区域が同じ行を読むこと）

## O1 からの注意（沖縄・端島）
- 端島（`landmark.hashima`）は名所で唯一中に入れる（`exteriorOnly` でない）。遠くは名所と同じく霧の先まで外観、40m 以内で中（3 棟・3 階）を描く。外観 約 5,300 三角形・中 約 1.1 万。描画は `render/tactical/enterables.ts` の `walked`
- 手がかりの掲示板・端島の船・秘蔵の物資の山は `render/tactical/stash.ts`（1 ドローコール）。タッチでは「E: 読む」「E: 船で渡る」「B: 受け取る」を押せるボタンが要る（`hud-act` の `data-kind` が `read` / `boat`、`hud-stash`）
- 手がかりの文（`.clue-note`）は幅 min(520px, 100vw−32px) で、360px でも折り返して収まる
